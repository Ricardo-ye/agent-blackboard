# 面向面试官的项目介绍：Agent Blackboard

## 项目整体介绍

**背景与目标。** 多个协作参与者共享任务和知识时，难点在于“写对但写坏”：并发更新互相覆盖、任务依赖被绕过、冲突缺少可追溯的处理过程。Agent Blackboard 是一个基于黑板模式的多智能体协作参考实现，目标是用明确规则保护共享状态，并让协作过程可观察、可测试。

**主要功能。** 系统包括 Agent 注册、心跳、能力匹配、任务依赖与自动分配、黑板条目 CRUD 和乐观锁、冲突检测/合并/投票/升级、动态规则，以及 WebSocket 实时事件流。

**技术栈与流程。** FastAPI 负责 API 与 WebSocket，Pydantic 做数据校验，aiosqlite 持久化，异步事件总线串接规则引擎和实时推送。典型流程是：注册能力 → 创建带依赖的任务 → 按能力和负载分配 → 写入黑板 → 触发规则/冲突处理 → 通过 WebSocket 观察事件。HTTP 请求、领域事件和推送通过 `X-Request-ID` / `trace_id` 关联。

## 我的职责与产出

建议基于当前仓库可验证产出表述为：

- 设计黑板、任务协调、规则引擎、冲突治理和 SQLite 存储的模块边界。
- 实现乐观锁 CAS、依赖检查、能力+负载分配、规则条件编译和事件发布链路。
- 建立 API、WebSocket、运行时边界和性能验证脚本，并把类型检查和集成冒烟接入 CI。
- 补充请求关联 ID、Prometheus 风格指标、灰度/回滚设计和可复现性能报告能力。

## 亮点与难点

| 亮点/难点 | 处理方式 | 价值 |
| --- | --- | --- |
| 并发覆盖 | 条目更新使用版本号和数据库条件更新 | 冲突显式暴露，不静默覆盖 |
| 依赖倒挂 | 创建与分配时检查依赖，循环依赖拒绝 | 防止“看似完成、实际不可执行” |
| 分配公平性 | 能力匹配、在线状态、当前负载共同排序 | 不单纯按抢单速度决定结果 |
| 可观测性 | HTTP 指标、事件丢弃计数、请求 ID 与 `trace_id` | 可以从请求追溯到事件和推送 |
| SQLite 边界 | 单条与批量写入分开压测、定义回滚判据 | 不把本地结果夸大为生产容量 |

## 优缺点与改进思路

| 维度 | 优势 | 不足 | 后续改进 |
| --- | --- | --- | --- |
| 设计 | 状态、规则、冲突边界清晰 | 当前规则是确定性的，不解决开放式自然语言规划 | 若有真实需求，以独立 Adapter 提供模型建议，核心仍执行确定性校验 |
| 性能 | WAL、批量提交、异步 I/O、性能脚本 | SQLite 单写入者限制多实例写入扩展 | 实现 PostgreSQL 后端与外部事件总线后再评估横向扩展 |
| 可维护性 | 分层、类型检查、测试与 CI | 运行时指标是进程内存态，性能基线历史仍需持续归档 | 保存结构化报告，部署后接入采集端和告警 |
| 产品验证 | 有可用性研究协议 | 尚无真实用户研究结论 | 招募 3–5 位参与者完成任务观察与复测 |

## 3–5 分钟口述版本

> 我做的是一个多智能体动态协作黑板系统。它解决的问题不是让多个 Agent “会思考”，而是让多个协作参与者修改同一份任务状态时，不会因为并发、依赖或冲突把状态写坏。
>
> 设计上我把系统拆成 Agent 注册、黑板条目、任务协调、冲突治理、规则引擎和事件总线。任务创建后会先验证依赖，再按能力标签、在线状态和当前负载选择候选者；黑板写入使用乐观锁，版本过期直接返回冲突，避免静默覆盖。规则引擎处理的是结构化事件和明确动作，所以它是一个确定性的协作 Workflow，而不是假装成 LLM 自主 Agent。
>
> 我比较重视可验证性：后端有 API、WebSocket、运行时边界和并发一致性验证；CI 会跑编译、类型检查、pytest 和集成冒烟。为了定位问题，我增加了 `X-Request-ID` 和事件 `trace_id`，可以把一次 HTTP 请求、领域事件和 WebSocket 推送串起来；性能脚本也能输出带环境信息的 JSON 基线。
>
> 这个项目的优势是状态治理和工程边界明确，限制也很清楚：它是单实例 SQLite 参考实现，不能把本地吞吐量当生产容量；目前也没有真实用户研究数据。下一步我会先做真实可用性测试，再根据写入压力决定是否引入 PostgreSQL 和外部事件总线。如果业务确实需要自然语言规划，我会把模型放在独立建议层，仍由现有规则和权限层决定是否执行。
