# Agent 与 Workflow 的边界

## 本项目的结论

Agent Blackboard 中的“智能体”是参与协作的工作单元，不是由大语言模型驱动的自主规划器。系统有明确状态、显式规则和可预测的副作用；因此在当前问题域中选择 **deterministic workflow + multi-agent coordination**，而不是让模型决定任务分配或冲突处理。

这不是能力缺失的掩饰，而是受问题边界约束的选择：同一共享状态被多个参与者修改时，首先需要的是可审计、可复现和可测试的协作治理。

## 已实现的确定性协作链路

1. Agent 注册能力、心跳与状态。
2. Task 声明依赖和所需能力；循环依赖被拒绝。
3. Coordinator 以能力匹配和负载排序选择候选者。
4. Rule Engine 以结构化条件和预定义动作处理事件。
5. Blackboard 通过乐观锁保护条目写入；Conflict Resolver 处理冲突。
6. Event Bus 将领域事件推送给 WebSocket 订阅者，并携带 `trace_id`。

## 为什么不是 LLM 自主 Agent

| 判断维度 | 当前项目 | 结论 |
| --- | --- | --- |
| 任务步骤是否可预测 | 注册、分配、状态流转、冲突解决均有明确状态机 | 用规则更可验证 |
| 错误副作用成本 | 错误分配或覆盖共享状态会破坏协作一致性 | 不应让模型直接执行写操作 |
| 是否需要开放式推理 | 当前输入是结构化能力、依赖、优先级和规则 | 不需要模型规划 |
| 是否需要解释与审计 | 需要定位具体规则、事件和写入版本 | 确定性路径更适合 |

## 未来接入 LLM 的前提

若未来引入自然语言任务拆解、非结构化能力抽取或辅助建议，应放在独立 Adapter 中：模型只提出候选建议，现有规则和权限层仍决定是否执行。不能让模型直接调用删除、规则修改、任务分配等写操作。

这样可避免把模型的不确定性耦合进黑板一致性核心，也能保留当前 REST 和 WebSocket 合约。
